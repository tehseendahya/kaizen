## Unit 1 — What is Computer Science? (L1)

### 1.1 What CS really is (and isn't)

**Abbreviations defined.** CS = Computer Science; algorithm = a finite, precise, step-by-step procedure that solves a class of problems.

**Key ideas.**
- CS studies specifying algorithms precisely and reasoning about their correctness and efficiency, not just "typing code."
- Computers require unambiguous instructions; humans tolerate vagueness.
- A program is one implementation of an algorithm; the algorithm is the recipe underlying many implementations.

**Intuition.** A cake recipe that says "mix until it feels right" is fine for a chef, not for a robot. CS turns the recipe into measurable steps: time, speed, temperature, stopping conditions.

**Worked examples.**
- **Sorting names.** Ten names → any simple method works. At scale (100M names), you must choose a design with predictable performance (e.g., mergesort with $O(N \log N)$ time; Big-O defined later).
- **Routing on a map.** For one driver, a greedy guess may work; for millions, you need graph algorithms (e.g., Dijkstra/A*), caching, and rate-limiting.

**Code sketch (pseudocode): precise vs vague**

```
vague_route(start, goal):
  drive generally toward goal; avoid bad traffic if you can

precise_route(start, goal):
  frontier ← priority queue ordered by (distance + heuristic)
  push(frontier, (start, 0))
  while frontier not empty:
    (u, cost) ← popMin(frontier)
    if u == goal: return reconstructPath()
    for each neighbor v of u:
      newCost = cost + w(u,v)
      if newCost < best[v]:
        best[v] = newCost; parent[v] = u; push(frontier, (v, newCost + h(v)))
```

**Visual/mental model.** Think of algorithms as contracts between human intent and machine execution: inputs, steps, outputs, guarantees.

**Common pitfalls.** Confusing "works for my input once" with "algorithm that works for all valid inputs and scales."

**Vocabulary.** algorithm; specification; implementation; pre/post-conditions; invariant; edge-case.

**Recap.** CS is about precision and scalability. Code is the vehicle, not the destination.

### 1.2 Why "scale" changes decisions

**Key ideas.**
- Scale amplifies everything. Small inefficiency × huge traffic = big cost. Small bias × many users = real-world harm.
- Measure with latency (time per request) and throughput (requests per second). Design for observability.

**Intuition.** A 50 ms inefficiency feels invisible in one request but totals hours of CPU per day at a million requests.

**Worked example.** If a handler wastes 50 ms per call: $1,000,000 \text{ calls/day} \times 0.05 \text{ s} = 50,000 \text{ s} \approx 13.9 \text{ CPU-hours/day}$.

**Fairness at scale.** Hiding 1% of artists in a recommender seems small; at 10M artists that's 100,000 people.

**Common pitfalls.** "It's just 50 ms." Always multiply by traffic.

**Vocabulary.** latency; throughput; P95/P99 (95th/99th percentile); bias; harm; telemetry.

**Recap.** Scale turns nuisances into failures—optimize hot paths and audit for fairness.

---

### 1.3 People & impact: re-identification and privacy

**Key ideas.**
- **Linkability:** quasi-identifiers (e.g., date of birth, ZIP code, gender) can re-identify "anonymous" data.
- Minimize collected data; separate identifiers; apply k-anonymity/differential privacy (both defined here).

**Intuition.** Each dataset is a puzzle piece. When joined, the picture (identity) becomes clear.

**Definitions.**
- **k-anonymity:** every record is indistinguishable from at least $k-1$ others on quasi-identifiers.
- **Differential privacy:** a randomized algorithm whose output distribution changes only slightly when one individual is added/removed (limits re-identification risk).

**Common pitfalls.** "We removed names, so it's anonymous." Not necessarily.

**Recap.** Correct + fast isn't enough; design for privacy by default.

## Unit 2 — Java & Object-Oriented Foundations (L2)

### 2.1 Values, variables, primitive types

**Abbreviations defined.** API = Application Programming Interface.

**Key ideas.**
- Type describes what a value is; value is the data itself.
- Java primitive types: `int` (whole), `double` (decimal), `boolean` (true/false), `char` (character code).
- Integer division truncates.

**Worked examples.** `3/2 → 1` (int), `3/2.0 → 1.5` (double), `1 + 2*3 → 7`.

**Pitfalls.** Accidental integer division; overflow of int (use long for big totals).

**Vocabulary.** literal; expression; precedence; cast; overflow.

**Recap.** Compute types consciously; promote to double when you need fractions.

---

### 2.2 Objects and references

**Key ideas.**
- Objects live on the heap; variables store references (think: sticky note pointing to an object).
- Create with `new`; use methods via `.`.

**Example.**

```java
String s = new String("Duke");
int len = s.length();
ArrayList<String> names = new ArrayList<>();
names.add("Ava");
```

**Mental model.** Reassigning a variable moves the sticky note; the old object remains unless referenced elsewhere (Garbage Collector may free it).

**Pitfalls.** Null references (NullPointerException); assuming assignment copies the object (it copies the reference).

**Vocabulary.** heap; reference; garbage collection; null; aliasing.

**Recap.** Distinguish objects from references to avoid aliasing bugs.

---

### 2.3 Equality: == vs .equals()

**Key ideas.**
- `==` compares references (same address?). `.equals()` compares values (same content?).
- Many standard classes override `.equals()` to be content-based (e.g., String, List).

**Example.**

```java
String a = new String("hi");
String b = new String("hi");
a == b       // false
a.equals(b)  // true
```

**Pitfalls.** Using `==` for strings from input; forgetting to override equals and hashCode together.

**Recap.** For content comparison, use `.equals()`.

---

### 2.4 What is a class? (state + behavior)

**Abbreviations defined.** OOP = Object-Oriented Programming.

**Key ideas.**
- **Class:** blueprint with state (fields) and behavior (methods).
- **Constructor** establishes a valid invariant (rules your object must always satisfy).

**Example.**

```java
class Course {
  private String title; 
  private int credits;   // state
  
  Course(String t, int c) { 
    title = t; 
    credits = c; 
  } // constructor
  
  int getCredits() { 
    return credits; 
  } // behavior
}
```

**Recap.** Think "blueprint → objects (instances) with guaranteed invariants."

## Unit 3 — Classes, Objects, and Project P0: Person201 (L3/L4)

### 3.1 What you'll build (and why)

**Abbreviations defined.** CSV = Comma-Separated Values; URL = Uniform Resource Locator.

**Key ideas.**
- Parse records from files/URLs → construct domain objects → compute on them (filter, distance, mapping).
- Keep the domain small and relatable to focus on core OOP.

**Example flow.** `"Ava,36.01,-78.92,Ginger&Soy"` → `new Person201("Ava",36.01,-78.92,"Ginger&Soy")`.

---

### 3.2 Encapsulation and immutability

**Key ideas.**
- **Encapsulation:** keep fields private; expose needed behaviors; reduce surface area for bugs.
- **Immutability:** object state never changes after creation → simpler reasoning, thread-safety bonuses.

**Example.**

```java
final class Person201 {
  private final String name, eatery; 
  private final double lat, lon;
  
  Person201(String n, double la, double lo, String e) { 
    name = n; 
    lat = la; 
    lon = lo; 
    eatery = e; 
  }
  
  String name() { return name; }
  String eatery() { return eatery; }
}

// "Changing" eatery creates a new object:
Person201 p2 = new Person201(p.name(), pLat, pLon, "Sazon");
```

**Pitfalls.** Public fields; setters that violate invariants (e.g., negative latitude).

**Recap.** Hide details; prefer immutable value types when practical.

---

### 3.3 Constructors and invariants

**Key ideas.**
- Validate once in the constructor so every instance starts valid.
- Mark truly read-only fields `final`.

**Checklist.** Null checks, range checks (lat, lon), normalization (trim names).

---

### 3.4 Printing objects: toString() and the Hollywood Principle

**Abbreviations defined.** Hollywood Principle = "Don't call us; we (the framework) will call you."

**Key ideas.**
- Override `toString()` for friendly debug/UX; used implicitly by printing/logging APIs.

**Example.**

```java
public String toString() {
  return name + " @(" + lat + "," + lon + ") likes " + eatery;
}
```

---

### 3.5 Workflow that won't fight you

**Abbreviations defined.** VCS = Version Control System.

**Key ideas.**
- Project layout: `src/` (code), `data/` (inputs), `lib/` (jars).
- Use Git branches per feature; small commits with messages explaining why.
- Run provided tests (e.g., Gradescope) early and often.

**Pitfalls.** Long-lived branches without merges; committing secrets; ignoring failing tests.

## Unit 4 — Arrays, ArrayLists, Sets, and "no duplicates" (L4)

### 4.1 Arrays vs ArrayList

**Key ideas.**
- **Array:** fixed length, contiguous, great when size is known. Syntax: `T[] a = new T[n];` Access with `a[i]`.
- **ArrayList:** resizable wrapper over an array; add/remove/size are convenient.

**Choice rule.** Known, fixed size → array. Changing size → ArrayList.

**Pitfalls.** Off-by-one indices; forgetting that `ArrayList.remove(i)` shifts elements.

---

### 4.2 Set: the easiest way to eliminate duplicates

**Key ideas.**
- Set stores unique elements. `HashSet` gives average $O(1)$ add/contains.

**Example.**

```java
Set<String> seen = new HashSet<>();
for (String w : words) seen.add(w);
```

**Pitfalls.** Expecting deterministic iteration order from HashSet (use LinkedHashSet to preserve insertion order).

---

### 4.3 Reusable patterns

**Process first-time-seen only**

```java
List<String> out = new ArrayList<>();
Set<String> seen = new LinkedHashSet<>(); // preserves order
for (String w : words) 
  if (seen.add(w)) 
    out.add(w);
```

**Skip adjacent duplicates (when input sorted)**

```java
for (int i = 0; i < words.size(); i++) {
  if (i > 0 && words.get(i).equals(words.get(i-1))) 
    continue;
  // process words.get(i)
}
```

---

### 4.4 Private helpers keep code readable

**Key ideas.** Small testable helpers reduce bugs and cognitive load.

**Example.**

```java
private static boolean isVowel(char c) { 
  return "aeiouAEIOU".indexOf(c) >= 0; 
}
```

## Unit 5 — Strings, Text Processing, and First Efficiency (L5)

### 5.1 A reliable strategy for "TxMsg" style problems

**Key ideas.**
- Split → transform each token → rejoin.
- Centralize rules in `txWord`; factor micro-checks (isVowel, isLetter, etc.).

**Sketch.**

```java
String[] toks = line.split(" ");
List<String> out = new ArrayList<>();
for (String w : toks) 
  out.add(txWord(w));
return String.join(" ", out);
```

**Edge-case cues.** First/last character handling; punctuation; capitalization; empty tokens.

---

### 5.2 Two String APIs you'll use constantly

- `split(regex)` → array of substrings.
- `String.join(delim, pieces)` → single string.

**Mini example.** CSV to semi-colon separated

```java
String out = String.join(";", "a,b,c".split(","));
```

---

### 5.3 Moving between arrays, lists, and sets

**Example.**

```java
String[] arr = {"a", "b", "a"};
List<String> list = new ArrayList<>(Arrays.asList(arr));
Set<String> uniq = new LinkedHashSet<>(list); // dedupe, keep order
List<String> back = new ArrayList<>(uniq);
```

---

### 5.4 Why naive string concatenation is slow

**Key ideas.** String is immutable → `text = text + piece` copies characters each time → quadratic work.

**Better pattern.**

```java
StringBuilder sb = new StringBuilder();
for (String p : pieces) 
  sb.append(p);
String text = sb.toString();
```

**Performance intuition.** Total copied characters with `+` ~ $1+2+…+N = O(N^2)$; with StringBuilder ~ $O(N)$.

## Unit 6 — ArrayLists, Maps, and Efficiency

### 6.1 From string building to Big-O

**Abbreviations defined.** Big-O notation: upper bound on how runtime grows with input size $N$ (ignoring constants/lower-order terms).

**Key ideas.**
- Repeated `+` concatenation → $O(N^2)$.
- StringBuilder append → $O(N)$.

**Micro-refactor.** Replace inside-loop `out += w;` with `sb.append(w);`.

---

### 6.2 ArrayList growth: amortized constant time

**Abbreviations defined.** Amortized = average per operation across a sequence.

**Key ideas.**
- `ArrayList.add` is usually $O(1)$; occasional resize copies elements → still $O(1)$ amortized.
- Inserting N items by appending is $O(N)$ overall.

**Pitfalls.** Repeated `add(0, x)` (front insertions) → $O(N)$ each due to shifting.

---

### 6.3 Maps 101: safe updates

**Key ideas.**
- `Map<K,V>` stores values by key; `HashMap` gives average $O(1)$ get/put.
- Use `getOrDefault`/`merge` to avoid NullPointerException.

**Pattern.**

```java
Map<String, Integer> freq = new HashMap<>();
for (String w : words) 
  freq.put(w, freq.getOrDefault(w, 0) + 1);
```

**Iteration.** `for (var k : freq.keySet()) { … freq.get(k) … }`

**Pitfalls.** Mutating a map while iterating without using an iterator; forgetting equals/hashCode for custom keys.

---

## Unit 7 — Maps under the hood: hashing and buckets

### 7.1 Intuition for hashing

**Abbreviations defined.** hash code = deterministic integer derived from a key; bucket = index in the underlying array (hash % tableSize).

**Key ideas.**
- Lookup: compute bucket index → scan small bucket → compare with `.equals()`.
- Good hashes spread keys evenly → short buckets → average $O(1)$ operations.

**Mental image.** A row of lockers (buckets). A key's hash tells you which locker to open; you only search inside that locker, not the whole school.

---

### 7.2 From client to implementer

**Key ideas.**
- HashSet/HashMap give average $O(1)$ for add/contains/get/put.
- Collisions are handled with small chains (conceptually: linked lists or trees for long chains in modern Java).

**Example (index positions).**

```java
Map<String, List<Integer>> positions = new HashMap<>();
for (int i = 0; i < words.size(); i++)
  positions.computeIfAbsent(words.get(i), k -> new ArrayList<>()).add(i);
```

**Pitfalls.** Custom key classes must implement consistent equals and hashCode.

## Unit 8 — Big-O and the Markov warm-up

### 8.1 From intuition to formalism

**Key ideas.**
- As $N$ grows, leading terms dominate: $3N+44$ and $15N+2$ are both $O(N)$; $N^2 − 6N$ is $O(N^2)$.
- Big-O abstracts machine speed; compare algorithmic growth, not seconds on your laptop.

**Vocabulary.** Big-O (upper bound), Big-Omega (lower bound), Big-Theta (tight bound) — you'll mostly use Big-O in 201.

---

### 8.2 Unique-words example: ArrayList vs HashSet

**Key ideas.**
- `ArrayList.contains` scans linearly → inside a loop becomes $O(N^2)$ worst-case.
- `HashSet.add` is average $O(1)$ → whole pass $O(N)$.

**Code contrasts.**

```java
// O(N²)
List<String> uniq = new ArrayList<>();
for (String w : words) 
  if (!uniq.contains(w)) 
    uniq.add(w);

// O(N) average
Set<String> uniq2 = new HashSet<>(words);
```

---

### 8.3 A note on dynamic dispatch

**Abbreviation defined.** Dynamic dispatch = runtime selection of the method implementation based on the object's concrete class.

**Key idea.** The call `x.contains(y)` resolves differently for ArrayList vs HashSet at runtime.

**Pitfall.** Assuming the compile-time type decides behavior; it's the runtime object.

## Unit 9 — Map review, anagrams, and "arrays as maps"

### 9.1 Map concepts reinforced

**Patterns.** Iterate `keySet()` for summaries; `entrySet()` when you need keys and values; `putIfAbsent`/`computeIfAbsent` to build lists of things by key.

---

### 9.2 Anagrams via a canonicalized key

**Key ideas.**
- Canonicalize each word (e.g., sort letters) and use that as the map key; value = list of words with that signature.

**Example.**

```java
Map<String, List<String>> anas = new HashMap<>();
for (String w : dict) {
  String key = sortLetters(w); // "listen" → "eilnst"
  anas.computeIfAbsent(key, k -> new ArrayList<>()).add(w);
}
```

**Encapsulation tip.** A tiny `AnaWord` value class can hide "sorted vs original" and define equals/hashCode by the sorted form.

---

### 9.3 Safer insertion: putIfAbsent vs containsKey

```java
m.putIfAbsent(k, new ArrayList<>());
m.get(k).add(v);
```

Avoids extra lookups and temporary objects.

---

### 9.4 "Arrays as maps" for character counts

**Key ideas.** `char` is essentially an integer index → `int[]` can act like a tiny map for fixed alphabets.

**Example.**

```java
int[] counts = new int[256];
for (char c : headline.toCharArray()) 
  counts[c]++;
```

**Pitfall.** Assuming ASCII (0–127) when input may be Unicode; size your array or use a `Map<Character, Integer>` if needed.

## Unit 10 — Big-O review, Map gotchas, and SUHA

### 10.1 Safer counting with getOrDefault/merge

**Patterns.**

```java
counts.put(w, counts.getOrDefault(w, 0) + 1);
// or
counts.merge(w, 1, Integer::sum);
```

Prevents null math.

---

### 10.2 Big-O practice patterns

**Rules of thumb.**
- Count constant-time work per iteration → multiply by number of iterations.
- Nested loops over same range often $O(N^2)$.
- Divide-and-conquer (e.g., mergesort) → $O(N \log N)$.
- Shrinking-step loops (`i *= 2`) → $O(\log N)$.

**Pitfalls.** Hidden linear scans inside "helper" calls (e.g., contains on a list) can blow up complexity.

---

### 10.3 Why HashMap is "O(1) on average" and when it isn't

**Abbreviation defined.** SUHA = Simple Uniform Hashing Assumption — hash codes distribute keys uniformly across buckets.

**Key ideas.**
- Under SUHA, bucket sizes stay constant on average → get/put/contains are average $O(1)$.
- Worst-case (adversarial collisions) degrades toward $O(N)$ per op; modern Java treeifies long buckets.

**Pitfalls.** Poor custom hashCode; mutable keys used in maps.

## Cross-unit Big Picture

- **Design for scale:** correctness + efficiency + safety (privacy/fairness).
- **Pick the right structure:** arrays (fixed), ArrayList (dynamic), Set (uniques), Map (associations).
- **String work:** prefer StringBuilder for loops.
- **Hashing:** think in buckets; know average vs worst-case.
- **Reason explicitly:** compute Big-O by counting, not guessing.

## Teaching Tips (if you're leading a study session)

1. Start with concrete demos (e.g., deduping names with Set) then peel back to the why (hashing and Big-O).
2. Use before/after code to show performance wins (string `+` → StringBuilder).
3. Make aliasing visible: pass a List to a method and mutate it; discuss references.
4. Trace a few steps of Dijkstra/A* on a tiny grid to connect "algorithms" with "precision under scale."
